Oracle redo logs

How Oracle makes a commit both fast and safe, why our local database kept stalling during bulk runs, and what we changed.

The short version

  • The redo log is Oracle's write-ahead journal: every change is described in it before the change counts as done.
  • A commit only waits for its redo to reach disk. The changed table and index blocks are written later, in the background.
  • Redo is written to a small set of files used in a circle. A file can only be reused once the changes it describes are safely in the data files (a checkpoint).
  • If the files are too small, Oracle runs out of reusable ones and every commit waits. That is what happened on our local Oracle Free with its two 10 MB files.
  • If a crash happens, Oracle replays the redo at startup, so nothing committed is ever lost.

Why a journal at all

A table's rows live in blocks spread across data files. One transaction can touch blocks in many places: the row itself, a few index entries, the undo segment that remembers the old values. Writing every one of those blocks to disk before saying "committed" would mean many small writes to scattered places, and each one waits for the disk.

Instead, Oracle writes a short description of each change to one file, always at the end. Appending to the end of one file is the fastest kind of write a disk does. The scattered block writes still happen, but later and in bulk, while nobody is waiting for them.

The price is a rule Oracle never breaks, called write-ahead logging: the description of a change must be on disk before the changed block may be written to its data file. That rule is what makes the shortcut safe.

What a commit does

  1. Change. Your session changes the blocks in memory (the buffer cache). They are now "dirty": newer in memory than on disk.
  2. Describe. For every change it also writes a redo record into the log buffer, another area of memory.
  3. Commit. The log writer process (LGWR) writes the log buffer to the current redo log file. Your commit returns as soon as that write is on disk. The time you spend waiting is reported as log file sync.
  4. Later. The database writer processes (DBWn) write the dirty blocks to the data files, in big batches, whenever it suits them.

LGWR does not only write at commit. It also writes every three seconds, when the log buffer is a third full, and just before DBWn writes a dirty block (the write-ahead rule). Because of that, the redo of a big transaction is usually on disk long before its commit, and the commit itself is quick. When many sessions commit at the same moment, LGWR writes all their redo in one go; this is called group commit.

What is in a redo record

A redo record is not the SQL you ran. It is a list of change vectors, each saying, at the level of a single block, "in block X of file Y, change these bytes to these values". One UPDATE of one row typically produces change vectors for:

  • the table block holding the row,
  • each index block whose entry changed,
  • the undo block where the old value is kept (yes, changes to undo are protected by redo too),
  • the transaction table that records the transaction's state.

Because redo describes physical block changes, replaying it is mechanical and fast: no SQL is parsed or optimised again. Every record gets a system change number (SCN), Oracle's logical clock, so changes can be replayed in exactly the order they happened.

Groups, members and the circle

Online redo logs come in groups. Oracle needs at least two. LGWR writes to one group at a time, the CURRENT one. When it is full, Oracle does a log switch and carries on with the next group; after the last group it goes back to the first.

Status in v$logMeaningCan it be overwritten?
CURRENTLGWR is writing to it now.No
ACTIVEFull, but some of the changes it describes are not yet in the data files. It is still needed if the instance crashes.No, not until its checkpoint finishes

A group can have several members: identical copies, ideally on different disks. LGWR writes to all of them at once, so losing one disk does not lose committed work. Production databases usually have two members per group. Our local Oracle has one, which is fine for a laptop.

Checkpoints

A checkpoint is the point up to which every change is safely in the data files. Oracle moves it forward continuously: DBWn keeps writing dirty blocks, oldest changes first. At every log switch, Oracle also makes sure the checkpoint soon passes the end of the group it just left. Once it has, that group is no longer needed for crash recovery and becomes INACTIVE.

So two things race each other: LGWR filling the other groups, and DBWn writing out the changes described in the group LGWR wants to reuse. While DBWn wins, nobody notices. When LGWR wins, the database has nowhere to write redo, and it has to stop.

When commits wait

Oracle measures what sessions wait for. These are the waits that belong to redo:

Wait eventWhat is happeningUsual cause
log file syncA session waits for LGWR to write its redo at commit.Very many small commits, or a slow disk.
log file parallel writeLGWR itself waits for its write to finish.Disk speed. This is what log file sync is mostly made of.
log file switch (checkpoint incomplete)LGWR wants to switch, but the next group is still ACTIVE. Every session that generates redo stops.Groups too small or too few for the redo rate.
log file switch (archiving needed)The next group is not archived yet (ARCHIVELOG mode only).Archiving cannot keep up.
log buffer spaceThe log buffer is full and LGWR cannot empty it fast enough.A huge redo rate, or a slow redo disk.

The expensive one is checkpoint incomplete. The others slow down one session at a time. This one pauses everybody who wants to change anything, until DBWn catches up.

What we saw in this project

During the performance runs (20,000 accounts, each producing an upgrade request, an outbox event, a welcome letter, more events and audit rows), the communication service could not go faster than about 140 letters a second, whether we ran one copy of it or two. Oracle's own wait statistics showed why.

Two problems, one per row:

  • Tiny redo logs. Oracle Free ships with two groups of 10 MB. Under our load each filled in seconds, the other group's checkpoint was rarely done in time, and everything paused for about 0.3 s at most switches.
  • Too many commits. Every Kafka event was its own transaction, so about 120,000 commits each waited for LGWR.

Sizing redo logs

  • Aim for a log switch every 15 to 20 minutes at the busiest time of day. Count your switches per hour (query below) and size from that.
  • Have at least three groups. With two, the one LGWR wants next is always the one that was just being filled, and it has the least time to be checkpointed.
  • Bigger does not mean more redo. The amount of redo depends only on the work done. Bigger files only mean fewer, calmer switches.
  • Bigger does not mean slower recovery, as long as Oracle checkpoints continuously. The parameter fast_start_mttr_target lets you ask for a recovery time; with it set, v$instance_recovery.optimal_logfile_size suggests a size. On our local Oracle it is 0 (not set).
  • Put redo on fast storage and keep it away from the data files. Every commit waits on it.

You cannot resize a group. You add new groups of the new size, switch until the old ones are INACTIVE, and drop them. That is exactly what our script does.

Redo and undo

The names are easy to mix up. Both are needed, for opposite jobs.

RedoUndo
RemembersHow to do a change againHow to take a change back
Kept inOnline redo log files (and archived copies)Undo segments, inside the data files
Used forReplaying committed work after a crash or restore; standby databasesROLLBACK; giving queries a consistent view while others change rows; rolling back unfinished work after a crash

Crash recovery

Say the machine loses power while transaction A has committed and transaction B is half way through. On the next start, Oracle repairs itself without any help:

  1. Find the starting point. The control file records the last checkpoint. Everything before it is already in the data files.
  2. Roll forward. Oracle reads the redo from the checkpoint to the end of the current group and re-applies every change, committed or not. This also rebuilds the undo for B.
  3. Open the database. Users can work again; the next step happens in the background.
  4. Roll back. Using the undo, Oracle takes back everything B did, because B never committed.

Result: A's changes are all there, B's are all gone. This is why only the redo between the last checkpoint and the end of the log has to survive a crash, and why ACTIVE groups must not be overwritten.

Archived redo logs

Online redo logs only reach back to the last checkpoint. To recover from a lost disk, you need more: a backup of the data files plus every change since that backup. In ARCHIVELOG mode, an archiver process (ARCn) copies each group to an archive location after a switch, and Oracle will not reuse the group until the copy is made. With a backup and the archived logs you can:

  • restore a lost data file and roll it forward to the moment of failure (media recovery),
  • restore to any earlier point in time, for example just before a bad deployment,
  • feed a standby database that replays the same redo (Data Guard),
  • read the changes as a stream: Oracle LogMiner, GoldenGate and Debezium all read redo. This is the change-data-capture option we mentioned for publishing the outbox table.

Our local Oracle Free runs in NOARCHIVELOG mode, which is normal for a laptop: a crash is recovered, a lost disk is not. Every bank database runs in ARCHIVELOG mode.

Look at it yourself

Run these as SYS against the local Oracle: docker compose exec -T oracle sqlplus -s / as sysdba, then paste.

The groups, their size and status

SELECT group#, members, ROUND(bytes/1024/1024) AS mb, status
FROM   v$log
ORDER  BY group#;

Where the files are

SELECT group#, member FROM v$logfile ORDER BY group#;

Log switches per hour (aim for about 3 to 4 at peak)

SELECT TO_CHAR(first_time, 'YYYY-MM-DD HH24') AS hour, COUNT(*) AS switches
FROM   v$log_history
WHERE  first_time > SYSDATE - 1
GROUP  BY TO_CHAR(first_time, 'YYYY-MM-DD HH24')
ORDER  BY hour;

What sessions waited for since the database started

SELECT event, total_waits,
       ROUND(time_waited_micro / 1e6) AS seconds,
       ROUND(time_waited_micro / 1000 / GREATEST(total_waits, 1), 2) AS avg_ms
FROM   v$system_event
WHERE  wait_class <> 'Idle'
ORDER  BY time_waited_micro DESC
FETCH FIRST 10 ROWS ONLY;

SELECT log_mode FROM v$database;

The resize we did

docker compose exec -T oracle sqlplus -s / as sysdba < infra/oracle-init/02-redo-logs.sql

It adds groups 3 to 5 of 512 MB, switches and checkpoints until groups 1 and 2 are no longer needed, and drops them. Run again, it does nothing. A fresh Oracle volume runs it on first start. Dropping a group leaves its file on disk, so redo01.log and redo02.log (10 MB each) are still in /opt/oracle/oradata/FREE, unused.

Glossary

redo record
The description of one or more block changes, written before the change counts as done.
change vector
One block-level change inside a redo record.
SCN
System change number: Oracle's logical clock. Every change and every commit gets one.
log buffer
The memory area where redo records wait for LGWR.
LGWR
Log writer: the process that writes the log buffer to the current redo log.
DBWn
Database writers: the processes that write changed blocks to the data files.
ARCn
Archivers: copy filled redo log groups in ARCHIVELOG mode.
group / member
A group is one slot in the redo circle; members are identical copies of it.
log switch
LGWR moving from a full group to the next.
checkpoint
The point up to which all changes are in the data files.
group commit
LGWR writing the redo of many committing sessions in one write.
NOLOGGING
An option that skips most redo for some bulk operations. Faster, but those changes cannot be recovered from redo; not for business data.
