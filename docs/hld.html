ACCOUNT UPGRADE PLATFORM · HIGH-LEVEL DESIGN

High-level design

The nightly upgrade of bank accounts, from the Excel file to the welcome email and the audit trail. Generated from docs/hld.md on 2026-11-06: edit that file, then run python3 docs/build-hld-html.py.

StatusAs built, November 2026: main after PR #26, plus compact letters, partitioning and the audit archive (ADR-0020 to 0022). A learning project; see Risks and open items.
ScopeThe nightly upgrade of bank accounts, from the Excel file to the welcome email and the audit trail, and the ops console around it
DecisionsThe reasons behind this design are in the decision records (ADR-0001 to ADR-0019)
DetailsHow to run, configure and operate each part: README

1. Purpose

Every night the bank sends a file of accounts that are due for an upgrade (for example from SAVINGS to SAVINGS_PLUS). The platform:

  1. loads the file and checks every row;
  2. decides, per account, whether it is eligible, by the business's rules;
  3. upgrades each eligible account in the core banking system;
  4. emails each upgraded customer a welcome letter;
  5. records every step in an audit trail;
  6. lets the operations team watch all of this, and act on it, in an ops console.

5. Integration

5.1 Events (Kafka)

Every event is written to the producing service's outbox in the same transaction as the change it announces (ADR-0004), and every consumer handles it once, retries with backoff and parks what still fails on <topic>.DLT (ADR-0005). Events are keyed by what they are about (usually the account), so one account's events stay in order.

TopicProducerConsumersMeaning
account.file-loadedingestionupgrade, audita file is completely loaded (id, date, counts)
account.upgrade-rejectedupgradeauditan account is not eligible, with the reason
account.upgradedupgradecommunication, auditthe core system upgraded an account
account.upgrade-failedupgradeauditrefused, or gave up after the last attempt
notification.sentcommunicationaudita welcome email was accepted by the mail server
notification.failedcommunicationaudita welcome email failed for good
audit.user-actioningestion, upgrade, communicationaudita person ran a job, retried an upgrade or resent an email
upgrade.run-requestedupgradeevery upgrade copy (one group each)"run now" broadcast (ADR-0011)

Every event has the same envelope: eventId, eventType, correlationId, occurredAt, actor, data. The correlation id also travels in HTTP headers (X-Correlation-Id) and every log line, so one business action (for example one file) can be followed across services, logs and the audit trail.

6. Data

Each service owns its schema and creates it with Liquibase; no service reads another's tables (ADR-0003).

SchemaMain tablesGrows byPartitioned by (ADR-0021)Kept (ADR-0019)
ING_OWNERFILE_INGESTION_LOG, ACCOUNT_STAGING, INGESTION_ERROR, BATCH_*every row of every filestaging: one partition per filestaging and completed Batch records 30 days; file list and rejected rows kept
UPG_OWNERUPGRADE_REQUESTevery account every daymonth of business datefinished requests 400 days; pending never deleted
COM_OWNERLETTER_TEMPLATE (versions never change), WELCOME_LETTER (template version and values, about 35 bytes; ADR-0020)every upgraded accountmonth writtensent and failed letters 400 days
AUD_OWNERAUDIT_EVENT (insert-only, no personal data), AUDIT_ARCHIVEevery business eventmonth of the event400 days in the table, then forever in archive files (ADR-0022)
each of the aboveOUTBOX_EVENT, PROCESSED_EVENTevery event sent / handled—outbox 7 days after publishing; processed events 30 days

The daily clean-up drops a whole partition once all its rows are past the period and none is still needed (a pending request or letter keeps its month), then deletes the old rows left. Oracle adds partitions by itself. Without the partitioning option (Oracle Standard Edition) the tables stay unpartitioned and the clean-up only deletes rows.

Personal data: names and emails live in staging rows, upgrade requests and letters only, all with retention. Letters show only the last four digits of the account number. The audit trail holds codes, counts and masked text (ADR-0015).

8.3 What happens when something fails

FailureBehaviour
Core system down3 quick retries per account, then the account waits for the next run; 5 unreachable in a row stop the run; FAILED after 3 runs
Core system refuses an accountthat account FAILED at once with the reason; the others continue
An upgrade copy diesits requests are taken over by other copies after the 2-minute lease
The service stops between the core call and saving itthe request stays IN_PROGRESS; after the lease it is called again with the same idempotency key
Mail server downletters wait and are retried after 1, 2, 4, 8 minutes; FAILED after 5 attempts; not counted as the service being DOWN
An address the mail server rejectsthat letter FAILED at once
Kafka downevents wait in the outboxes (alert OutboxFallingBehind) and are sent when Kafka is back
An event that keeps failingparked on <topic>.DLT (alert EventDeadLettered); fix and replay
A letter template that cannot be filledthe event is parked before any letter points at that version; activate a fixed version and replay
An audit archive file that does not read back completenothing is dropped; the month stays in the table and is tried again the next day
Rows of an audit month change after it was archivednothing is dropped; alert AuditArchiveProblem for a person to decide
The same event twicerecorded once (processed-event table, unique keys)
A bad row in the filerejected with its problems; the rest of the file loads
A file that cannot load (not a workbook, a column missing)marked FAILED, moved to error
The same file again (another name)moved to error as .duplicate
Load stopped half waythe next run resumes after the last committed chunk
Ingestion down during planningthe event is retried with backoff
Redis downgateway: no sign-in; upgrade: calls go ahead without the shared limit (ADR-0012)
Oracle downeverything waits and retries; scheduled jobs try again at their next time

Delivery guarantees: events at least once, handled once; core calls at least once, made safe by the idempotency key; emails at least once (a crash after the mail server accepted but before the commit sends again).

8.4 Observability

  • Metrics: every service exposes Micrometer metrics to Prometheus, including the pipeline's own (core calls by outcome, limit waits, finished requests, lease takeovers, outbox backlog, events by result, emails, retention, partitions dropped, audit months archived).
  • Dashboard: "Account upgrade" in Grafana, a file in the repo; sign-in through Keycloak.
  • Alerts: eight rules (service down, dead-lettered event, Kafka lag, outbox stuck, core system unavailable, upgrade copy died, emails failing, audit archive problem), emailed by Alertmanager (ADR-0016).
  • Tracing a business action: the correlation id in every event, HTTP call, log line and audit row.
  • Audit trail: who did what and when, searchable by account, action, type or person (ADR-0015); older months in checked archive files, listed with their SHA-256 (ADR-0022).

12. Glossary

TermMeaning
Business datethe day a file is for (from its name), not the day it runs
Upgrade requestone account's upgrade for one business date: PENDING, IN_PROGRESS, UPGRADED, REJECTED or FAILED
Runone pass of the upgrade over everything PENDING; several copies can share it
Copyone running process of a service; the upgrade service is designed for several
Leasea copy's time-limited claim on a request (CLAIMED_BY, CLAIMED_UNTIL)
Outboxa table where events wait, written with the change they announce
